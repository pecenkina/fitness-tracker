# База данных и REST API первого релиза

[Начальная миграция PostgreSQL](../backend/migrations/001_initial.sql) создаёт таблицы одной транзакцией. Для проверки на новой пустой базе выполните из корня репозитория:

```sh
psql -d fitness_tracker_dev -v ON_ERROR_STOP=1 -f backend/migrations/001_initial.sql
```

## Модель

| Связь | Назначение |
| --- | --- |
| users → workouts, plans | Один пользователь ведёт свой журнал и хранит свои планы. Поля профиля находятся в users. Уникальность email проверяется без учёта регистра. |
| exercises ↔ muscle_groups | Таблица exercise_muscles задаёт целевые мышцы. Каждая мышечная группа относится к области тела. |
| plans → plan_exercises → plan_sets | Позиции сохраняют порядок упражнений и целевых подходов. Повторения и вес можно задать для каждого подхода отдельно. |
| workouts → workout_exercises → workout_sets | Независимые записи журнала с датой, состоянием, длительностью и подходами. |
| exercises → plan_exercises, workout_exercises | Планы и журнал используют общий локальный справочник. Ссылки защищают используемые упражнения от удаления. |

Позиции начинаются с 1 и уникальны внутри родителя. Вес задаётся в килограммах. Для упражнения с собственным весом можно явно указать 0 кг дополнительной нагрузки. Пустой вес означает, что значение неизвестно. Пара source и source_key служит ключом повторного импорта.

## Контракт для реализации Express

Базовый путь — `/api`. Идентификатор пользователя сервер получает из сеанса. Списки и вложенные изменения ограничиваются владельцем корневого объекта. Для отсутствующего и чужого ресурса ответ одинаковый — 404. До входа персональные маршруты возвращают 401. Проверка полей возвращает 400, конфликт уникального email — 409. Создание ресурса возвращает 201 с объектом и его id, удаление — 204.

| Метод и путь | Действие |
| --- | --- |
| POST /auth/register, POST /auth/login | Принимают email и password. Вход создаёт сеанс. |
| POST /auth/logout | Завершает текущий сеанс. |
| GET /me, PATCH /me | Возвращают и изменяют профиль. Доступные поля — birth_date, gender, height_cm, weight_kg, goal. Хеш пароля исключён из ответов. |
| GET /exercises, GET /exercises/:id | Каталог и карточка. Параметры списка — q, muscle_id, equipment, difficulty, goal. |
| GET /plans, POST /plans | Список своих планов и создание плана вместе с упражнениями и подходами. |
| GET, PUT, DELETE /plans/:id | Чтение, полная замена или удаление своего плана. |
| POST /plans/:id/workouts | Принимает workout_date, копирует упражнения и целевые подходы своего плана в новый черновик. Перед завершением пользователь подтверждает фактические результаты. |
| GET /workouts, POST /workouts | Журнал по убыванию даты и id с фильтрами from, to, status. Создание вручную. |
| GET, PUT, DELETE /workouts/:id | Чтение, полная замена или удаление своей тренировки. Для завершения передать status равный completed и минимум один записанный подход. |
| GET /exercises/:id/history | Свои завершённые подходы с датой, повторениями и весом. |
| GET /analytics/summary, GET /analytics/exercises/:id | Сводка за период и динамика выбранного упражнения по датам. |

Пример тела POST /workouts (exercise_id должен существовать в каталоге). Порядок элементов массива задаёт position.

```json
{
  "name": "Ноги",
  "workout_date": "2026-11-20",
  "status": "completed",
  "duration_minutes": 40,
  "exercises": [
    {"exercise_id": 1, "sets": [{"reps": 8, "weight_kg": 40}, {"reps": 6, "weight_kg": 45}]}
  ]
}
```

При PUT сервер блокирует корневую запись по id и user_id, проверяет тело и заменяет дочерние записи в одной транзакции. Клиент передаёт идентификаторы справочника, порядок и значения подходов. Идентификаторы владельца и дочерних строк сервер не принимает. Запуск по плану читает шаблон и его строки из одного согласованного снимка и атомарно сохраняет копию.

Пример запроса заголовка тренировки через pg. Параметры — id тренировки и id пользователя из сеанса.

```sql
SELECT id, name, workout_date, duration_minutes, status
FROM workouts
WHERE id = $1 AND user_id = $2;
```

## Вычисления

Обе границы периода включены и относятся к workout_date. В расчёты входят только завершённые тренировки текущего пользователя. Количество и длительность считаются по тренировкам до соединения с подходами. Пропуски длительности и веса исключаются из соответствующих сумм. Если нет ни одного измерения, сумма возвращается как null.

Объём подхода равен reps × weight_kg. Для примера выше общий объём — 590 кг, максимальный вес — 45 кг. Для графика рабочих весов API возвращает веса отдельных подходов по датам, для графика максимумов — наибольший измеренный вес за дату. Рейтинг содержит до 20 упражнений по максимальному весу за период, при равенстве сортируется по id. Для распределения нагрузки объём подхода делится поровну между целевыми мышечными группами упражнения. Упражнения без привязки попадают в группу «Не указано». Изменение записи сразу учитывается при следующем запросе.
